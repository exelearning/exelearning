# ADR-0001: Use source-aware preview filtering in the editor and opaque iframe isolation in embedded hosts

## Status

Superseded by [ADR-0002](ADR-0002-hybrid-preview-trust-boundary.md).

ADR-0002 keeps this record's source-aware filtering and embedded-host opaque
isolation, and extends it: enabling custom active content in web/server mode now
switches the preview to a self-hosted opaque snapshot (instead of running author
JavaScript same-origin with the editor). The residual risk this ADR called out —
"enabling custom JavaScript is a trust decision and does not make the project
safe", with author code reaching the editor DOM and cookies on enable — is what
ADR-0002 closes for web/server. The rest of this ADR (the filtering policy, the
non-mutation guarantee, the embedded-host lifecycle, the Electron restriction)
carries forward unchanged.

## Context

eXeLearning previews combine two sources with different trust levels. Official themes,
libraries, MathJax, and iDevice runtimes are maintained and distributed by the project and
must keep working. Authors can add active HTML through TinyMCE and HTML textareas, component
properties, custom head and footer fields, imported ELP/ELPX projects, and custom iDevices.

Executing author-controlled active content on the editor origin exposes the editor DOM,
project state, browser storage, and, in Electron, the preload bridge visible on the parent
renderer. PR #1968 addressed that risk by routing most runtimes through an opaque HTTP
preview protocol. Its layered fixed/session/generated resources, atomic incremental
revisions, transport providers, and Electron-specific serving substantially increased the
implementation and operational cost.

An editor embedded in an authenticated LMS or CMS has a different boundary. Preview content
must not receive the host application's origin, cookies, storage, CSRF tokens, or JavaScript
objects, even when the host intentionally permits author JavaScript to run inside the
preview.

## Problem

How can the normal editor preserve first-party preview behaviour while disabling
author-controlled active content by default, and how can embedded hosts isolate complete
previews without retaining protocol v2?

## Decision drivers

- Preserve existing official preview behaviour and export fidelity.
- Never mutate Yjs data or silently rewrite a project.
- Make execution of custom active content an explicit, limited trust decision.
- Keep authenticated host state outside the preview's origin.
- Minimize core transport and host-adapter complexity.
- Fail closed when an embedded host cannot provide the opaque boundary.

## Options considered

### Filter all final preview HTML

Rejected. A whole-document sanitizer cannot distinguish official eXeLearning scripts from
author content and would break maintained iDevice and theme behaviour.

### Route every runtime through opaque HTTP preview protocol v2

Rejected. It provides a browser-enforced boundary but requires layered resources, manifests,
revision synchronization, conflict recovery, multiple providers, and Electron-specific
serving for the ordinary editor preview.

### Source-aware filtering in normal preview plus opaque embedded snapshots

Chosen. A preview-only document adapter applies one parser-based policy to author-controlled
component HTML, component property strings, custom head content, and custom footer content.
Official resource files are not filtered. The adapter clones data and is used only by preview
generation; save and export continue to use the original document.

Embedded hosts receive complete preview snapshots through authenticated management routes
and serve them through unguessable, expiring, cookieless capability URLs. Their iframes omit
`allow-same-origin`. Updating a preview replaces the complete snapshot.

## Evidence

- The normal file-map preview is generated by
  `src/shared/export/exporters/Html5Exporter.ts::generateForPreview` and loaded by
  `public/app/workarea/interface/elements/previewPanel.js`.
- Author component content and properties enter the export model through
  `src/shared/export/adapters/YjsDocumentAdapter.ts`; custom head and footer values enter
  through the same adapter's metadata mapping.
- Official scripts are added separately by `PageRenderer`, `BrowserResourceProvider`, and
  `Html5Exporter`, so a document adapter can preserve their provenance.
- `app/main.js` configures the main Electron renderer with `preload.js`; the same-origin
  preview can reach its parent's exposed bridge even though Node integration is disabled.
- PR #1968 documents and tests opaque sandboxing, capability serving, CSP coverage, and the
  protocol-v2 implementation that this ADR simplifies.

## Decision

- Normal web, server, static/PWA, PHP-WASM, and Electron editor previews keep the existing
  normal preview transport.
- Trusted eXeLearning scripts execute normally.
- Author-controlled active content is disabled by default in the normal preview by a central,
  parser-based, preview-only policy.
- The UI identifies detected active content and requires an explicit enable action. Trust is
  scoped to the current project and application session, is cleared on project replacement,
  and is revoked on subsequent document changes.
- Stored Yjs content and generated exports remain unchanged.
- Electron does not offer enablement while its normal preview shares a renderer with the
  preload bridge. This restriction is preferable to adding another preview transport.
- Embedded LMS/CMS previews use an iframe sandbox without `allow-same-origin` and a minimal
  full-snapshot capability transport. Management is authenticated and CSRF-protected;
  serving is cookieless; capabilities expire and are cleaned up.
- No embedded integration may silently fall back to a same-origin preview.

## Consequences

### Positive

- Official preview behaviour remains compatible.
- Core no longer needs protocol-v2 layers, revisions, synchronization, or Electron serving.
- One source-aware policy covers the normal preview surfaces without changing saved data.
- Embedded host isolation relies on the browser origin boundary rather than sanitization.
- Host implementations use a small create/replace/serve/delete lifecycle.

### Negative

- Normal preview safety depends on maintaining a complete inventory of author-controlled
  entry points and dynamic insertion paths.
- Enabling custom JavaScript is a trust decision and does not make the project safe.
- Opaque iframes can limit selected browser features.
- Host plugins still need temporary storage, quotas, expiration, and cleanup.
- Electron users cannot run custom active content in preview without a future isolated
  renderer design.

### Neutral

- Published/exported content retains author JavaScript and has its own delivery trust model.
- Host frameworks may use different native storage and CSRF mechanisms while implementing
  the same lifecycle.

## Risks

An unclassified author field or an official runtime that inserts an unprepared property into
the DOM could bypass the normal-preview policy. Tests cover the known model fields and active
construct categories, and new author-editable HTML fields must be added to the adapter
inventory. Opaque previews can still initiate network requests or deceive users; the sandbox
does not claim to prevent those behaviours.

## Validation

- Unit tests verify scripts, event handlers, active URLs, SVG, `srcdoc`, plug-in elements,
  refresh, base elements, form actions, and legacy imports are detected and disabled.
- Adapter tests verify Yjs/export source objects are not mutated.
- The core Playwright test covers the warning, explicit enable/disable lifecycle, project
  scoping, and preservation of the stored and exported source.
- Host unit and integration tests cover authenticated management, capability serving,
  expiry, path validation, CSP headers, and snapshot creation/update/load/cleanup.
- A browser-level run against each real host remains a pre-merge validation requirement for
  official runtime behaviour, parent isolation, media, downloads, and message handling.

## Follow-up work

- Reassess Electron enablement only if preview content moves to a renderer without preload or
  native IPC exposure.
- Extend the author-content inventory whenever a new editable HTML or script field is added.
- Test opaque iframe feature compatibility before adding sandbox tokens or media bridges.
- Add host-native browser fixtures that exercise the complete management and serving routes
  in Moodle, WordPress, Omeka S, Nextcloud, and Procomún.
